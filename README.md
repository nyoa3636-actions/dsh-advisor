# dsh-advisor

A configurable **Executor / Advisor workflow for DeepSeek Harness (DSH)**.

`dsh-advisor` is a DSH port/adaptation of [philipbrembeck/pi-advisor](https://github.com/philipbrembeck/pi-advisor). The upstream project is MIT-licensed and remains the design reference for this fork.

The core idea is simple:

- Use a cheap/fast model such as GPT-5.6 Luna or DeepSeek V4.1 Flash as the normal **Executor**.
- Let the Executor read files, search, edit, run tests, and own the task.
- Call a stronger model such as GPT-5.6 Sol or another premium model only as an **Advisor** for consequential plans, repeated failures, or final review.
- The Advisor gives advice only. **There is no automatic takeover.**

## Status

Early DSH port with an in-Harness configuration surface. The runtime preserves the central flow semantics from `pi-advisor`:

- `ask_advisor` tool for voluntary second opinions
- plan / failure / completion consultation rules injected into the Executor prompt
- automatic repeated-tool loop gate
- **Advisor Settings page inside the DSH Settings surface** — model picker, reasoning effort, gates, and advanced options
- **Advisor consultation budget** — a cash ceiling, a consultation ceiling, session or project scope, and over-limit behaviour
- **usage dashboard, consultation history, and a Test Advisor button** in the same page
- `/advisor`, `/advisor-budget`, `/advisor-history`, `/advisor-log`, and `/advisor-test` session commands
- durable, deduplicated Advisor usage accounting with provider-reported token counts
- bounded reconstructed conversation context
- configurable tool-result disclosure (`full`, `summary`, `exclude`)
- optional Git working-tree context (`off`, `summary`, `full`)
- optional local secret redaction
- optional Executor pinning

Not yet ported from Pi-specific UX: Advisor Scout, Herdr integration, tracked/untracked file-content consent handoff, and Pi UI cards. These remain deliberately outside this port.

Everything runs inside DSH: the page is a `settings.section` contribution of this plugin, it reads DSH's own model catalog, and it reads and writes the plugin's own configuration entry through DSH's settings service. No external web server, companion app, or separate management UI is involved.

## Installation

Install the GitHub checkout into a DSH profile:

```sh
dsh plugin --profile default add github:nyoa3636-actions/dsh-advisor
```

Pin a branch or tag when you need an exact revision:

```sh
dsh plugin --profile default add github:nyoa3636-actions/dsh-advisor#feat/dsh-advisor-settings-budget
```

This package ships runnable JavaScript: the CLI half under `dsh/`, and the browser bundle as the committed build artifact `dsh/client.js`. A Git install needs **no** `prepare` build step and no pnpm `allowBuilds` permission.

Verify the layer:

```sh
dsh --profile default --dump-config
```

The composed profile gains one `dsh-advisor` row, and the Harness Settings surface gains an **Advisor** section once you open Settings.

## Development

```sh
npm run check          # syntax-check every module and verify dsh/client.js is current
npm test              # unit suites
npm run test:integration   # real cordis/Dsh runtime suites
npm run build:client  # regenerate dsh/client.js after changing anything under dsh/client/
```

`dsh/client.js` is generated by `scripts/build-client.mjs` from the modules under `dsh/client/`. DSH serves a package's `./client` entry as one standalone self-registering bundle, so the artifact must not contain `import`/`export` statements; the build inlines the modules and keeps React on DSH's browser module table. `npm run check` fails when the committed bundle no longer matches its sources.

## Advisor Settings page

Installing the bundle adds an **Advisor** section to the DSH Settings surface beside the built-in pages. It has four tabs:

| Tab | What it shows |
| --- | --- |
| **Settings** | Advisor on/off, the Advisor model picker, reasoning effort, Executor pinning, the consultation gates, the consultation budget, and one **Advanced settings** disclosure |
| **Budget** | Ceiling, spend, remaining budget, a usage progress bar, consultation count, remaining consultations, the last model and time, and the last result |
| **History** | The recorded consultations with time, reason, model, tokens, estimated cost, and success/failure |
| **Connection test** | A **Test Advisor** button that sends one short message to the configured model and reports the result |

Everything the page edits is persisted by DSH: the fields are declared volatile on the plugin's own configuration entry, so the page writes them through the standard settings service into the profile's patch file. There is no second settings store.

Model lists come from `ctx.remote.session.modelCatalog()`, so the picker only offers providers and models that DSH actually registered, and it only offers the reasoning efforts that model advertises. An unsupported effort is never sent: if a stored effort is not advertised by the newly selected model, the page falls back to the model default.

The **Advanced settings** disclosure exposes the remaining supported options: `contextMaxChars`, Git context and its cap, tool-result line/byte caps, the per-tool disclosure policy rows, secret redaction, `gateFailureMode`, `advisorBlockOnBlocked`, `advisorSessionSummary`, and `simpleMode`.

The `/advisor` command family exposes the same operations to a session, and the page uses it to read live budget data:

```text
/advisor status                     # budget and configuration report
/advisor off | on                   # Advisor enable/disable
/advisor model <provider/model>     # Advisor model
/advisor effort <name|default>      # Advisor reasoning effort
/advisor budget <on|off>            # consultation budget
/advisor scope <session|project>    # budget scope
/advisor limit <stop-advisor|confirm>
/advisor unknown-cost <allow|count-only|stop-advisor>
/advisor reset-budget               # clear the active scope
/advisor-history [count]            # recent consultations
/advisor-test                       # the same connection test as the button
/advisor-log on|off | git <level> | policy <tool> <policy> | policies
```

See [docs/dsh-advisor-settings.md](docs/dsh-advisor-settings.md) for the field-by-field reference.

## Configuration

The bundle inserts a `dsh-advisor` row. Configure it in the profile's `cordis.patch.yml` or in `$DSH_HOME/cordis.patch.yml` by overriding that row id. Do **not** insert a second row with the same id.

```yaml
- id: dsh-advisor
  config:
    advisor: openai-codex/gpt-5.6-sol
    advisorEffort: high

    # Leave executor empty to follow the DSH model picker.
    # This is recommended if you want to switch to Sol/Astra manually.
    executor: ''
    executorEffort: ''

    contextMaxChars: 15000
    advisorPlanGate: true
    advisorFailureGate: true
    advisorCompletionGate: true
    advisorAutoLoopGate: true
    advisorLoopThreshold: 3
    advisorMaxCallsPerSession: -1

    # Consultation budget (see below).
    advisorBudgetEnabled: false
    advisorBudgetMaxUsd: 0
    advisorBudgetMaxCalls: -1
    advisorBudgetScope: session
    advisorBudgetLimitMode: stop-advisor
    advisorBudgetUnknownCost: allow

    # Automatic loop-gate failure/block behavior.
    gateFailureMode: block-tool
    advisorBlockOnBlocked: true

    advisorGitContext: summary
    advisorGitContextMaxChars: 20000
    advisorToolResultMaxLines: 2000
    advisorToolResultMaxBytes: 51200
    advisorRedactSecrets: true
```

DSH applies profile/home patches after bundle layers. A later row with the same `id` overrides the bundle row's configuration; its `config` value is replaced as a whole rather than deep-merged. The Advisor Settings page writes the same row, so a page edit and a hand edit address one document.

`gateFailureMode: block-tool` and `advisorRedactSecrets: true` are the recommended defaults for new installs. A profile that already pins either key keeps its own value: the recommendations are applied only when the key is absent.

Model references use `provider/model` because DSH routes models through provider registrations. Replace the examples with routes that exist in your DSH model picker.

### Executor selection and manual takeover

For the intended workflow, leave `executor` empty and select Luna / DeepSeek V4.1 Flash normally in DSH. `dsh-advisor` then leaves DSH's model selection untouched.

If `executor` is set, the plugin pins every Executor request to that provider/model. That is useful for a fully automatic cheap-Executor setup, but it also means a manual model-picker switch will be overridden on the next request. Therefore **leave `executor` empty when you want to decide takeover yourself**.

## What the Executor sees

When an Advisor is configured, DSH receives the same central guidance used by upstream `pi-advisor`:

- consult before committing to a materially consequential plan;
- consult after two materially equivalent failed attempts, a recreated failure, or two actions with no measurable progress;
- consult before declaring success for non-trivial work;
- use `ask_advisor` with an empty object for a normal contextual review, or attach a concise `draft` / specific `question` when useful.

Example tool call conceptually:

```json
{
  "question": "Is this state-management change safe across process restart?",
  "draft": "Move the cache ownership into Repository; validate with existing integration tests.",
  "gitContext": "summary"
}
```

The Advisor response is returned to the Executor as a normal tool result. The Advisor has no mutation tools and does not take over the session.

## Automatic loop gate

By default, after three consecutive calls with the same normalized tool signature, `dsh-advisor` asks the Advisor whether the Executor should continue.

The Advisor must begin with one of:

```text
Decision: proceed
Decision: revise
Decision: blocked
```

- `proceed` — reset the repeat counter and allow the tool call.
- `revise` — deny that repeated call and return the Advisor feedback to the Executor.
- `blocked` — apply `gateFailureMode`.

`gateFailureMode` can be:

- `block-session` (default): deny this and subsequent tool calls in the session. With `advisorBlockOnBlocked: true` (default), the active turn is also cancelled while queued future input is preserved.
- `block-tool`: deny only the current repeated tool call.
- `warn-and-continue`: log the warning and allow execution.

No case automatically switches the Executor to the Advisor model.

A `block-session` decision remains sticky for the current live Agent. Recover by starting a new session or by resuming the persisted session into a new live Agent. A DSH `clear` lifecycle edge also resets the state when a surface emits it. Compaction deliberately does **not** reset blocked state, call budget, repetition tracking, or usage accounting. `/advisor reset-budget` clears the consultation budget for the active scope without touching the session itself.

The recommended default for a new install is `block-tool`, which denies only the repeated call. An existing profile that pins `gateFailureMode` keeps its value.

## Context sent to the Advisor

The plugin reconstructs the model-visible DSH conversation from `agent.session.deriveMessages()` and keeps recent complete entries up to `contextMaxChars`.

It follows upstream's disclosure shape:

- ordinary user text
- Executor visible text
- Executor tool calls
- tool results, capped at 2,000 lines / 50 KiB by default
- optional working-tree summary or patch
- optional Executor `draft`
- optional targeted `question`

Reasoning blocks are not forwarded. Conversation, draft, and repository regions are escaped before tagged prompt insertion. Repository text is explicitly labelled as untrusted data. Optional secret redaction runs locally before disclosure.

## Tool-result policies

Per-tool policies can be configured:

```yaml
advisorToolPolicies:
  bash: summary
  read: full
  deploy: exclude
```

- `full`: include bounded output.
- `summary`: include only status / size metadata.
- `exclude`: withhold the tool call/result content from Advisor context.

## Consultation budget

The consultation budget tracks **Advisor calls only**. Executor tokens and cost are never counted here.

```yaml
advisorBudgetEnabled: true      # master switch
advisorBudgetMaxUsd: 5.00       # cash ceiling in USD; 0 = no ceiling
advisorBudgetMaxCalls: 40       # consultation ceiling; -1 = no ceiling
advisorBudgetScope: session     # session | project
advisorBudgetLimitMode: stop-advisor   # stop-advisor | confirm
advisorBudgetUnknownCost: allow        # allow | count-only | stop-advisor
```

- The cash ceiling and the consultation ceiling are independent; either can be unset.
- **Session scope** tracks one DSH session. **Project scope** shares one budget across every session whose workspace resolves to the same Git work tree root (or the same workspace path when there is no repository). `advisorProjectKey` overrides that identity explicitly.
- The ledger is persisted as JSON under the harness home (`advisorLedgerPath` overrides the location). Resuming or compacting a session never resets it.
- `advisorMaxCallsPerSession` is still honoured: when the budget is off it is the only call ceiling, and when the budget is on it becomes the default consultation ceiling. Existing profiles keep working unchanged.

### What the ceiling can and cannot promise

Cost is computed from the token usage the provider reports, multiplied by the rates you configure or that DSH exposes:

```yaml
advisorPricing:
  openai-codex/gpt-5.6-sol:
    input: 0.0000025
    output: 0.00001
    cacheRead: 0.00000025
    cacheWrite: 0.000003
```

The Advisor Settings page edits the same rates as one row per model under **Model rates** (`provider/model: input, output, cacheRead, cacheWrite`).

- A price is **never invented**. A model without configured rates records its tokens but reports its cost as unknown.
- Before a call, the plugin reserves the ceiling it can prove (`context window × input rate + default output × output rate`). Concurrent sessions therefore cannot both spend the same remaining budget.
- A cash ceiling is only displayed as an **exact** limit while every settled call carried a price. As soon as one call is unpriced, the total is labelled `Estimated` and the dashboard says so.
- `advisorBudgetUnknownCost` decides what an unpriced model does: `allow` records the call and marks the total estimated, `count-only` does the same and never claims an exact ceiling, and `stop-advisor` stops Advisor consultations once a price is unknown.

### Over-limit behaviour

- `stop-advisor` (default): Advisor consultations stop. The Executor keeps working normally, `ask_advisor` returns a "continue without the Advisor" result instead of failing the session, and the automatic loop gate withdraws the Advisor instead of blocking the tool call.
- `confirm`: the same, except DSH asks the user before spending past the ceiling. Declining changes nothing else about the session.

The budget never escalates into a session stop. `block-session` remains available through `gateFailureMode` and is always an explicit choice.

### Pricing and history

Every Advisor call records the provider/model, input and output tokens, cache read/write tokens when the provider reports them, the estimated cost, the time, the outcome, and the reason the consultation happened. The **History** tab and `/advisor-history` show the same records.

## Why this fork exists

The original experiment behind this fork tried to keep a premium model as the main agent and semantically compress large tool results before returning them. In testing, when the premium model needed exact/full content it often re-read the source, causing the worker call plus summary plus full premium read — sometimes consuming more tokens than a normal read.

`dsh-advisor` reverses the architecture: a cheap model owns the large-context implementation work, while the premium model receives only bounded context for high-value judgment.
